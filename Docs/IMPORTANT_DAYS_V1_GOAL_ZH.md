## 2. 完整产品目标与范围锁

配套设计是完整产品规格；本文不替代它，只将实现责任和默认决策收敛。必须覆盖：

- 三种创建预设：期待某一天、记住一个起点、每年纪念；一份日子支持已过/下次周年两种视角。公历/农历、已知/未知年份、自然日口径及特殊日期处理完整。
- 成长页在体重后、Quiet Wins 前增加同级列表入口。Today 在目标/标记后、周/月习惯前，最多两行；候选为空整段隐藏。不增 Tab，不挤占原工具栏，不改变 Record 直接图文记录的主路径。
- 一张轻量表单，名称和有效日期即可保存；更多设置后置。提供实时日期预览、管理列表、搜索、常看顺序、编辑、归档、删除、详情与失败恢复。示例不落入用户库。
- Entry 双向引用；从日子写新记录默认今天，从旧 Entry 创建日子需确认实际发生日。关系不复制正文/图片、不改 Entry 类型/来源/原时间或技术更新时间。
- 用户主动创建一次性关联 Todo，复用现有编辑器；用正确的有类型关联，不能冒充 `TodoTaskSource.entryID`。不做相对日期同步、自动年度任务或级联完成/取消。
- 本地提醒：默认关，当天或提前 1/3/7 天等少量选项，最多两次、默认建议 09:00 可修改。与 Todo、每日记录、周回顾共享容量和提交协调，实际状态可检查。
- 两种桌面组件：指定日子（小/中尺寸，日历数字/照片两种样式）；日子清单（中尺寸，用户选择并排序最多三个）。照片样式与清单均是 V1 必选项，不留成未实现占位。
- 独立封面、全局搜索结果、稳定 ID 路由、备份/恢复、覆盖升级、中文/英文、浅深色/系统着色适配、大字号与基础无障碍。

不做：目标截止日期与自动倒数、Habit 自动起点/重置、百日千日提醒、联系人/系统日历导入、复杂分类/完整日历、社交/情侣/云同步、AI、主题商店、视频、Live Activities、独立 Watch/Mac App 或锁屏组件全家桶。也不顺便重构整个 AppShell、导航框架、通用关系平台或全部通知业务模型。

普通 UI/内部类型名、间距、色彩与布局细节可自主决定；保持既有风格，不为偏好问题反复询问 Owner。建议名称上限 80 字符；与仓库实际规范冲突时选一致的明确上限并记录。主要设计默认值按配套规格执行，不把必选项降为“以后再做”。

## 3. 必须落地的业务契约

### 3.1 日期、来源与事实

- 民用日期、历法、年份是否已知、年度规则和显示视角分开保存；倒数、周年数、下一期、排序均派生，禁止每天写回原始事实。
- 经过 N 个自然日与第 N 天分开；V1 只用前者。今天显示“就是今天”，次日才切年度下一期；起点翌日已过 1 天。不能以秒差/86400 代替自然日，也不能每年固定加 365。
- 未来预定日过去后用“预定日已过”，不声称事情发生、旅行开始、Goal 完成或 Habit 持续。转为真实起点必须由用户明确确认日期。
- 未知年份仅算下一次，不使用虚构年份推算年龄、周年或已过天数。
- 2 月 29 日在非闰年、闰月缺席、农历三十不存在必须显式确认规则并预览，不能让框架自动溢出跨月。农历闰月一年最多对应一次纪念。详情可查看已选规则。
- 用固定且解释清楚的中国农历转换基准（建议 Asia/Shanghai）产生公历民用日期，再按用户当前自然日比较；原日子不因旅行改写。准确处理农历年份/闰月，不把循环年份字段误当普通公历年。
- 在实现文档写清经过验证的日期范围和边界行为；正常生日/起点场景不能因偷懒被裁掉。超范围明确提示不支持，不猜测。农历期望值取独立权威样例并记录来源，测试运行离线；不能用被测函数生成自己的 golden 值。

### 3.2 Today、管理列表与详情

- Today 设置：自动（今天及未来 7 自然日）、始终显示、不显示。先排除归档/不显示，再按今天→始终→自动近期排序；平局稳定，最多两条。普通旧起点不会自动长期占位。
- 常看只控制管理页次序，不暗含 Today、通知或桌面授权；列表同一日子只出现一次，年度项目归入下一次日期组。
- 详情的主要按钮是写记录，不是装修卡片。独立有效数据集按 ID 解析，不用 Today 前两条/组件前三条充当数据仓库。
- 对纪念期次采用轻量可选关联：默认关联日子本体；明确写某年纪念记录时保存该期实际民用日期，通用记录不猜年份。回看可按明确期次/年份过滤，不自动每年建虚拟 Entry 或额外日子。
- 外部路由不能清空正在写的 Record 草稿或任意现有编辑器状态，不能绕过迁移/恢复界面。冷启动、已打开详情、来源删除后都有确定落点；不要求开发一套全新的全局路由平台。

### 3.3 Entry / Todo / Quiet Wins

- 两端 ID 的关系防重复；双方删除只清理引用，不级联删除对方。实际新增 Entry 和关系应有清晰事务/恢复边界，保存失败不伪称全部成功，避免重试重复记录。
- 从日子写“今天的感想”，不能自动回填成多年以前。关联/解除关系不会修改 Entry 原文、发生时间或外部来源。
- 相关 Todo 仍使用现有服务、历史事件和编辑交互。日子改期不自动改 Todo；提示原计划仍在，给检查入口。已完成/取消 Todo 不被新功能复活。
- 新建/收藏/改样式/经过天数都不是 Quiet Wins 成果。用户实际创建的普通 Entry 按旧规则计入；外部分享仍依当前真实来源证据处理；一个 Entry 关联多个日子不重复计数。
- 保留已接受的 Goal 时钟回拨 P2、旧 Weekly Review 布局警告与备份来源缺失边界。不要重新开启无关“全库质量整改”；若本改动使旧问题扩大或产生新的数据/语义回归则必须修。

## 4. 实现结构、数据与隐私

### 4.1 模型、历史 Schema 与备份

- 使用独立日期实体和必要的有类型关系/封面所有权。复用现有服务和存储方式，不通过伪 Entry、Tag、Todo 隐藏字段冒充日期，也不引入另一套事实 JSON 库绕过迁移。
- Owner 已授权本功能所需的新 Schema 与备份版本；先核对实际版本链，再以明确新版本扩展。尤其注意仓库历史 Schema 可能共享模型类型：不能改一个旧 Entry/Goal 类型就无意改变所有历史 checksum。冻结已发布 Schema 定义，不破坏 `preMigrationProtection` 路径别名修复及恢复保护。
- 原 Bundle ID、主库路径、数据容器、App Group 标识不变；不为 Widget 迁移主库，不重置模拟器以掩盖覆盖升级失败。全部开发验证使用隔离合成库，不访问真实私人库和 iPhone 数据。
- 新备份完整覆盖日期事实、规则、关系、常看/展示/提醒偏好、独立封面与所有原来已支持的内容。旧支持包仍可读，新包有明确版本；旧 App 不支持新包就明确拒绝，不伪造兼容、静默遗漏。
- 当前 v7 不序列化 CaptureImportReceipt 的已接受边界不属于本轮修复；新格式扩展不能伪造历史来源，亦不得把仍存在的恢复来源缺口称为“完全无损”。默认沿用既有来源字段/恢复语义，精确记录新格式是否继承该限制。保护原有明确可恢复的数据和当前本地收据排除行为。
- 恢复后重建组件数据、重新协调本设备通知。备份中的提醒偏好不是通知“已成功排期”的证据。覆盖恢复的语义沿用现有服务，不暗改成另一种合并/删除策略。

### 4.2 封面

- 原 Entry 图片可作为来源，但显式“用作独立封面”后有独立所有权。复用已存在的安全复制、校验/缩略图机制，不借用 Entry 的级联删除关系。
- 从照片选择/裁切、更换、取消、保存失败、低空间、删除、恢复均验证。封面事实进入备份，组件小图可重建；不创建隐藏图片 Entry 以复用图库。
- 用户删除日子只清理其自有资源；删除来源 Entry 不删除已保存的独立封面。暂存文件与已提交文件的清理边界明确，重复重试不泄漏大图。

### 4.3 Widget 只读投影

- 使用同一套纯日期计算模块，App/Today/通知/Widget 不能各自实现一份日期语义。
- 新增 Widget Extension target 是已授权范围。保留主 App/Share Extension 的现有身份与版本号；Widget Bundle ID 从实际主 App ID 派生，使用既有 App Group。尽早核对 target、scheme、embed、entitlements 与 Debug/Release 配置，不等最后发布才检查。
- 主 App 成功保存后原子发布有版本/生成标识的最小展示快照和必要小图；Widget 不打开主 SwiftData，不执行迁移/恢复，不消费 Share Inbox。不要复制全库正文/原图到共享区。
- 明确用户主动选择组件日子才构成外部展示授权。需要可选项目目录时只发布授权日子的最小元数据；不以“配置方便”为由自动公开全部私人日子。详情中的组件准备/预览可以承担这个确认，不额外增加长向导。
- 快照应能生成后续时间线，不是写死数字或整图。默认不依赖用户每天打开 App；使用当前 SDK 支持的标准机制，拒绝后台常驻/秒级刷新假设。
- 保存、改期、删除、归档、撤回桌面可见性及恢复后重建；旧异步结果不得覆盖新版本。删除/隐私撤回需优先撤销旧可读内容并请求刷新，失败可诊断，不无限使用旧私密缓存掩盖问题。系统可能暂存已渲染画面，不能承诺立即远程抹除，明确区分 App 可控文件与系统显示时机。
- Widget 故障不影响主 App 记录/打卡。缓存损坏、缺图、未知版本、删除/归档/失效 ID 中性降级；不自动替换为另一个私人日子。
- 数字样式信息层级清晰；照片支持裁切/遮罩；清单最多三个且手动排序。中英文长标题、极大天数、系统着色/深色、可访问性尺寸可读。只参考用户截图的结构，不复制 Days Matter 的图片、商标或整套皮肤；截图未随仓库发布，不应等待 Owner 再上传。
- 组件 Gallery 只用合成示例；通知通用描述选项与隐私敏感机制配合。组件添加帮助不能把“展示说明”谎称成“已自动添加”。不增加在线图片库、账号或 AI 依赖。

### 4.4 提醒协调

- 基于现有通知客户端/调度逻辑做最小共享协调：权限、容量和异步提交串行化；保留各业务前缀和 Todo 期次规则，不复制两个独立 60 条调度器，也不 `removeAll`。
- 现有 60 条是 App 保守预算，不是本 Goal 声称的系统硬限制。计算全部实际 pending，确定性选择近期请求；实际容量不足、拒权、失败、已过期都诚实显示。
- 不让一个模块驱逐其他模块请求后，后者仍显示 scheduled。若协调导致请求被移除，必须同时刷新相应状态；测试交错更新与旧结果覆盖。
- 通知失败不回滚已保存日子；提示“日子已保存，提醒尚未排期”。区分偏好、规划和系统实际 pending；先显示下一次时间，提交后复核。
- 年度规则能被验证可靠地表达为系统重复触发时可用重复；其他采用有界预排/补齐，避免无界填满队列。显示实际覆盖范围和下一次请求；“长期不打开”不能伪装成无限保证。
- 编辑、删除、归档、关闭、规则变化、时区/重要时间变化和恢复都要撤销旧请求并复核。点击旧通知安全降级。专注模式、系统渲染/递送时机不能由单测宣称真机通过。

## 5. 自主实施顺序

### 启动与关键风险前置（轻量）

读相关实际代码，建立文件责任与验收映射。优先定位 Schema/备份版本链、通知共享协调边界、Widget target/共享目录可行性与草稿路由，不做全面架构重写。必要技术资料仅查官方文档或一手日历资料；不引入未授权外部库。

尽早用小型编译/结构检查核对 Widget target，而不为基线反复跑全量测试。账号/签名不可用可先继续无签名与模拟器工作，留下 Owner Gate，不能假装已有 TestFlight 证明。

### 内部里程碑 A：App 内完整路径

日期计算与测试 → 新实体/迁移/备份/封面 → 创建/管理/详情/搜索 → Entry 与一次性 Todo 关联 → Today → 提醒协调。顺序可以按依赖微调；各逻辑变更小提交和定向测试。迁移、通知、数据关联在扩散到更多 UI 前做一次独立风险审查。

A 结束保留 checkpoint、运行涉及范围的集成验证，自动进入 B；不发“请确认继续组件”的问题。

### 内部里程碑 B：组件与整体验证

完成数字/照片/清单、用户配置、原子快照、时间线、路由、隐私/失效降级、添加引导；验证实际 App/Widget 打包结构与 Share Extension 共存。对照完整规格做范围复核，再集中回归和最终独立审查，处理发现的问题。

不以“App 内基本可用”宣告 V1 完成，不把照片或清单变成下个 Goal。确有环境缺失则逐项列出，完成所有不依赖该环境的工作。

## 6. 开发—独立 Review—修复闭环

使用当前 Codex 环境实际可用的独立 agent/session 承担审查；不要假装一定有某个 CLI 命令/模型，也不要为了审查偷偷更换付费方案。实现者对合成测试负责，审查者必须独立读固定 SHA 的真实 diff、受影响周边代码和证据，不只是复述实现者报告。

至少覆盖两个互补审查视角，可由独立 reviewer 分轮完成：

- 数据/规则：日期、旧 Schema、升级/恢复、封面、来源证据、通知交错、错误与取消。
- 产品/集成：五 Tab/Today/Record、Entry/Todo、Quiet Wins、组件路由/隐私/打包、长文本与系统渲染。

审查者不直接修改其负责审查的实现；发现项提供严重度、文件/行号、可触发情景、证据和最小修复目标。主 agent 核实、补反例、限定修复；审查者针对新 SHA 复审受影响项。不要无条件接受误报，也不要只改测试预期、删断言或跳过失败。

收口要求：没有未关闭的本次引入 P0/P1；日期错误、数据丢失、隐私泄露、基本流程损坏不得降级。影响已批准必选场景的 P2 也修；可接受的轻微视觉/平台限制明示，不做无穷 polish。保留原来已接受的基线限制，不主动扩修。

review/修复/commit/push 都不是人工停点。通常 1–3 轮收敛；若同一问题两轮仍无实质进展，先做限定根因诊断；若继续需要改变范围/数据保证或遇无法验证的关键环境，再以具体证据阻塞，不能无限循环或只因达到轮数就假称完成。

若环境根本不支持独立 reviewer，完成能做的实现和测试，标明 `REVIEW_BLOCKED`，不把另写一段自评叫“独立审查”。Owner 只在真正的权限、认证、风险/范围决策或最终真机边界介入。

## 7. 测试策略与证据要求

### 成本控制

- 无代码改动的启动/文档/Git 操作不补跑全套旧基线。
- 日常改动只跑受影响单元/集成/UI。日期纯逻辑可频繁验证；数据库与通知先用合成 fixture/注入客户端；不靠真等到午夜。
- A 结束不要求全项目 Unit+UI；已有覆盖足够只跑关键跨模块定向集成。
- 功能基本收敛并处理主要 review 项后，安排一次全量 Unit + 一次集中关键 UI；不是每个里程碑反复全量。先用本仓库实际测试清单，不硬编码旧的 324/325 等数量。
- 集中后小修只重跑受影响项；如果改了迁移、备份或共享通知等广泛路径，由风险说明决定是否必须再次完整回归。不能为省时保留未知关键失败，也不能机械全跑。
- 最终在精确可追踪 HEAD 做 Debug/无签名 Release、必要无签名 generic-device build 与 App/Share/Widget 包含关系检查。不得执行 `archive`、上传或推 tag。无签名构建不是签名/真机/Cloud PASS。

### 必要覆盖矩阵

| 范围 | 反例/结果 |
| --- | --- |
| 日期 | 当天/翌日/年末、2月29日三种规则、未知年份、农历跨年/闰月/缺三十、独立样例、支持范围边界 |
| 时间 | 固定时钟、时区旅行、夏令时23/25小时、系统回拨；保存的原日不变；旧 Habit 日期证据不被改写 |
| UI | 三种预设、最短保存路径、取消/防重复、无数据、Today>2条/同日平局/隐藏/常看、中文英文长名/大字号 |
| 关联 | 新记录今天、旧记录实际日期确认、一条Entry多个日子、不改原时间/来源、双端删除、期次过滤、返回搜索定位 |
| Todo | 创建/取消/失败、改期不自动联动、独立完成/删除、既有重复Todo行为和历史不回归 |
| Quiet Wins | source=nil分享收据与URL来源、直接文字/图片正对照、排名变化后详情、删除/撤销、后台导入主线程、关联不重复计数 |
| 通知 | 拒权/排期失败/容量满/多类别交错、旧结果不覆盖新请求、关闭/删除不删其他类别、next实际pending、覆盖范围 |
| 媒体 | 选图/裁切/取消/换图/低空间/删来源/删日子、封面独立所有权、重试清理、备份校验 |
| 升级与备份 | 用旧基线实际磁盘库合成数据覆盖升级；相关v11历史变体/支持旧包；新包→空库恢复→重开；全关系/封面/旧数据保持，继承限制明示 |

| 隐私与恢复 | 缺图/坏快照/未知版本/缓存写失败/旧版本异步覆盖/撤回授权/删归档/恢复；不自动换私人日子、不读取主库 |

记录每次关键运行的命令、SHA、环境/目标、通过/失败/跳过数、exit code、日志/xcresult路径。保留最初失败与根因，不能把多次定向集合拼成“最终全量全绿”。审查不等于重新运行测试；签名/真实Cloud/物理手机/长时间挂桌面没有做就标 NOT_RUN 或 OWNER_DEVICE_GATE。

日志脱敏：诊断只记阶段/版本/错误码/必要计数，不落真实日子名、生日、记录正文/照片。真实用户数据和账号密钥不进 Git。合成小型 fixtures 与可复现脚本可以提交；大量运行产物留本地并在报告给路径。

## 8. Git 交付与可续接

已授权在 `codex/important-days-v1` 做合理 commit、普通 push、新建/更新一个 Draft PR（base 固定见开头）。不需要每次请求确认；可在里程碑 push，不能把 push/PR 当作执行完成。不得修改旧 PR #8/#9 的 head/base/state、目标分支或描述，不 merge main，不 force-push，不删分支、不打任何 tag。

开发只追加与本目标有关的提交。更新 Foundation 的最小批准增量、`Docs/INDEX.md`、`CURRENT_STATE`、`CURRENT_TASK` 以及以下新交付文档，均限工作分支：

- `Docs/IMPORTANT_DAYS_V1_EXECUTION.md`：进度、决策、恢复点、实际SHA/环境。
- `Docs/IMPORTANT_DAYS_V1_REVIEW_ZH.md`：独立审查轮次、固定范围、问题关闭及证据边界。
- `Docs/IMPORTANT_DAYS_V1_ACCEPTANCE_ZH.md`：需求→实现→测试映射、已知限制、四个日子的最小 Owner 清单。

文档应短而真实，避免每步追加重复流水账。允许把证据索引合并组织，但不能丢失固定SHA/失败/剩余边界。最后文档提交可能与已审产品SHA不同：明确区分 product/test SHA 和 delivery SHA，并核验中间只有文档变更；不要用自引用hash或未提交修改伪造同源证明。

网络/认证失败：区分可重试网络与需Owner认证，有限重试（例如最多3次）；保留本地提交，继续能离线完成的范围。续接先查实际branch/HEAD/工作树/PR/已完成项，不盲目 `git pull`、不从头重跑测试或重新开发。外部提交结果不确定先查询远端再重试，避免重复 PR/重复提交。

`EXECUTION` 始终包含：已完成、进行中、最后验证的确切SHA、剩余工作、外部阻塞、下一条具体动作。若执行中断，新会话读固定 Goal 后沿同分支同 PR 继续；不得改用另一个产品基线。

## 9. 停点、状态与最终报告

正常终点：`READY_FOR_OWNER_DEVICE_GATE`。条件是 V1 必选实现完成、可执行的自动化/构建门禁通过、独立审查已收敛、远端普通 push/新 Draft PR 核对成功。此状态表示可由 Owner 决定后续发布和真机验收，不表示 TestFlight/签名/真机已经通过。

其他真实状态：`PARTIAL_WAITING_ENVIRONMENT`（缺Xcode/模拟器等关键验证）、`REVIEW_BLOCKED`、`BLOCKED_AUTH_OR_PUSH`、`BLOCKED_OWNER_DECISION`。把具体缺项与已完成部分分开，不能只因预计能完成就标 COMPLETE，也不能因设备Gate未授权而放弃所有可完成实现。

最终中文报告至少包括：

1. Goal结果与A/B范围完成情况；尚未完成项。
2. repo、branch、product baseline、goal snapshot SHA、product/test SHA、delivery SHA、工作树与upstream、Draft PR及base。
3. 用户可见变化：页面位置、两种组件/三种表达、记录与待办协同。
4. Schema/备份版本、历史数据和封面保护、当前继承限制。
5. 实际自动化/构建结果、未运行门禁、证据路径；不混算跨SHA测试。
6. 独立审查者/轮次/范围、已修问题、剩余非阻塞限制；缺独立审查就明说。
7. 最小Owner真机清单：未来旅行、过去起点、农历生日、已有图文周年；重点实际桌面/通知/草稿与原App覆盖，不让Owner重做几十种代码侧边界。
8. 明确未执行：旧PR修改、merge/tag/Archive/TestFlight、账号协议/证书改动、真实手机/私人库操作。

除系统权限与明确决策外，不要求Owner每个阶段回答“继续吗”。到最终停点停止扩展，不自动进入发布或下个功能。
