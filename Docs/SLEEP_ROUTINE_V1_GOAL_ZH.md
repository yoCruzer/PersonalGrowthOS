## 4. 开发—独立审查—限定修复闭环

默认配置一名主实现者 + 一名真正独立的只读Reviewer；同一Reviewer可分两轮覆盖数据和产品，不为了形式同时开很多agent。不强制具体模型/速度档，不自行更换订阅；使用环境实际可用能力并如实记录。

发现项写严重度、文件/行号、触发条件、证据和最小目标。主实现者核实，补生产路径反例，限定修复；Reviewer复审新的固定SHA和受影响范围。允许驳回有证据的误报；不能以修改断言、跳过失败或只测复制出来的纯模型掩盖实际接线错误。

通常有限轮次收敛；同一问题两轮没有实质进展时改做限定根因诊断，而不是无限扩大测试。只有权限、账号、不可逆风险、实际范围冲突或关键环境缺失才升级；阶段结束、commit、push或Reviewer要求局部修复都不是人工停点。

不要因为旧任务使用 `READY_FOR_INDEPENDENT_REVIEW` 就在内部开发完成后等Owner搬运review；本轮要求在Codex内部完成独立审查—修复闭环。环境确实不支持时才如实 `REVIEW_BLOCKED`。

其他状态：`BLOCKED_ENVIRONMENT` / `BLOCKED_AUTH` / `REVIEW_BLOCKED` / `PARTIAL_WITH_EXPLICIT_GAPS`，写明已完成项和真实阻塞，不伪称完成，也不以普通复杂度为由只交计划。

最终中文报告控制篇幅，包含：

1. Goal结果、分支/精确SHA/新Draft PR、工作树与远端同步状态。
2. 晨间路径是否完整、剩余产品项/独立审查结论。
3. 实际测试与构建分轮结果、失败如何闭合，未执行项明确列出。
4. 原始重要日子功能及旧数据升级/备份的组合验证范围；不能把未知手机版本假定为V12。
5. 一个紧凑Owner清单：先保护并核对旧数据，晨间直接记录并重开；重要日子另做原关键冒烟，实际通知/组件另行观察。
6. 明确未merge、未tag、未Archive/发布、未操作真实手机/私库。

停止后不自行开始时间投入、复杂睡眠分析或下一功能。后续是否通过Xcode直接安装或通过testflight-标签发布，由Owner另行授权。本次目标是把真实首次使用之前的实现/审查/自动化工作闭合，不给Owner增加一长串本可自动完成的操作。
