## 一、定位与长期边界

在随心log内部新增相对独立的「时间投入」模块，先由 Owner 个人每日使用，记录阅读、学习、运动、Coding 等主动投入以及活动体验。未来妻子有明确需要时，可扩展为代两个孩子记录课外学习、运动、阅读等，但本期不开发孩子管理 UI、家庭协作，也不同时开发独立 App。功能无需 AI、互联网或 Apple Intelligence，核心路径离线可用。

核心问题：在某个项目上已经记录了多少投入，近期节奏如何，每次做了什么、有什么感受？累计时长不等于技能水平；不强制连续打卡，不把无记录称为未行动。计时记录活动，不监控手机使用；启动后允许锁屏、切换其他 App、正常工作生活。个人 Coding 记录不自动吸收 Codex/机器任务的运行时长。

与睡眠、Habit、Todo、Goal、Entry 独立，不把睡眠计入投入，不自动完成习惯/任务/目标，不自动增加 Quiet Wins 成果，不重复写多份时长事实。跨模块引用以后按实际需要增加，非本期必选；文字体验在本模块即可独立保存。

V1 的规划能力止于单次倒计时目标与回顾：长期累计是必选，周目标、阶段目标、时间预算、日历排程明确后置，不能宣称本版已提供完整规划系统。

## 二、身份、事实与存储契约

### 2.1 参与者不等于记录者

每条正式记录和未完成计时都有稳定 participantID。V1 UI 只使用「我」，不出现成员管理；核心服务、冲突检查、汇总均显式限定参与者，不能将设备持有人写死为活动参与者，也不能用「大宝阅读」这种项目名称代替人物身份。

建议独立实体，实际 SwiftData 类型名可遵循仓库规范：
- Participant：稳定 ID、显示名、默认参与者身份标记/等价持久选择、排序/归档状态。
- Activity：稳定 ID、名称、可选轻量分类或图标、归档状态；它是可长期累计的投入项目，不是一次记录。
- InvestmentSession：稳定 ID、participantID、activityID、时间证据类型、实际时长、发生日期/原时区、来源、createdAt/updatedAt、可选体验和备注。
- RunningTimer：独立、可恢复的未完成操作；包含稳定操作/会话 ID、participantID、activityID、模式、有效计时段/检查点、目标时长、状态与修订信息。未完成状态不作为正式历史记录累计。

「我」采用惰性、幂等初始化：展示页面和显示推荐活动不预先落库；首次实际创建活动/计时/记录时才原子地取得或创建默认参与者。新装空库必须仍可通过现有备份恢复入口。恢复含参与者的新包时采用包内稳定身份；旧包缺少此模型时按同一惰性规则建立，不按名字合并、不重复生成「我」。不为孩子预造档案或事实。

同一参与者最多一个未完成计时；running、paused、到目标待确认、结束待保存、异常待复核都占用该名额。启动另一项目时显示已有状态，由用户先处理，不静默覆盖。不同参与者的服务层状态互不阻塞：以两个合成 ID 测试即可，不因此增加家庭 UI。

### 2.2 时间与来源不能互相冒充

区分事实发生时间、实际填写时间和技术更新时间。备注或体验编辑不移动发生日期；no-op 保存不制造新事实，技术更新时间遵循仓库现有单调规则。

时间证据至少区分：
- 有可信起止的有效区间/计时段：保存原始时区及绝对时刻，暂停段不贡献时长。
- 仅日期与时长：允许「昨天阅读 45 分钟」，不虚构 09:00–09:45。
- 用户修正后的纯时长：从计时结果改成另一个时长、但没有提供相应有效区间时，明确转为这种精度；保留 timer 来源与修正标记，不把旧区间重新拉伸、按比例分配或继续展示为已确认的精确证据。

正式累计只有一份权威时长。具有有效区间时必须与区间之和一致；仅改总时长时按所选发生日记录，不同时保留相互矛盾的权威区间。用户可显式改归属日期、活动及时间证据，但不能由后台处理悄悄修改。

时长在核心和导出中统一单位与精度（建议整数秒），展示层统一格式化；不足一分钟不能静默变成零或丢弃。拒绝负数、非有限数、溢出、非法区间和伪造的未来完成事实；异常长计时先进入复核，不自动截断或自动入账。回拨导致既有事实落在当前时钟之后时保留并标明异常，不能清洗历史来凑统计。

### 2.3 模块独立，不等于新建事实主库

复用同一 SwiftData 存储、版本化迁移和统一备份，不新增第二套 JSON 事实主库，不复制为 Entry/HabitLog。界面草稿与持久对象分离；不能直接编辑受自动保存影响的共享模型，再声称取消等于撤销。

计时写入和取消/失败回滚只能影响自己的操作。可用同库独立 ModelContext 或现有等价机制，不允许一次计时失败的 context.rollback() 撤销 Record、睡眠等编辑，也不允许计时自动保存顺便提交它们的草稿。无需为本期重构通用框架或强制拆 Swift Package。

## 三、V1 必选交互与计时生命周期

### A. 正计时、倒计时和持久化结束

- 常用活动卡可直接开始正计时；快速新建活动后可开始。手工记录入口与「开始计时」并列，不藏成故障补救。
- 倒计时提供简单常用目标（例如 25/40/60 分钟），支持提前结束、暂停和继续。目标是有效投入时长，不含暂停。
- 显示依据保存的锚点/检查点计算，不依赖后台持续循环，不申请无关后台模式。锁屏经过时间按同一规则处理；壁钟变化、单调计时与设备重启连续性须可测试。不能将不可证明的跨进程/跨重启锚点差值当作精确时长。
- 每次开始、暂停、恢复、结束先完成相应持久化，再宣告成功。写入失败提示失败并保留上一个可恢复状态，不展示虚假的保存/暂停成功。

倒计时采用固定的保守规则：
1. 25 分钟目标在后台停留 50 分钟后回来，默认待确认投入为 25 分钟，不是 50 分钟；状态为「到目标，待确认」，不是正式已完成记录。
2. 到目标由有效时间证据推导，不要求后台到点回调或通知恰好执行。暂停时间不消耗目标。
3. 提前结束按实际有效时长；用户可修正并保存，也可明确选择继续正计时，从点击继续的时刻开始新有效段，不自动补上到目标至点击继续之间的空白。确实投入的额外时间可由用户显式补记/修正。
4. 本期不以新增后台通知为必选；前台和返回时必须清楚显示到目标状态。没有通知权限不妨碍记录，不能承诺一定后台响铃。若在范围内附带本地提醒，必须复用现有共享协调器并补相关回归，不新建抢占旧通知的调度器。

结束采用可恢复的两阶段确认：
- 点「结束」时冻结本次有效时长并持久化为待保存状态，然后显示简洁确认卡；反馈和备注不必填，确认即可保存。
- 确认卡停留、关闭、切 Tab 或冷启动都不继续累计。关闭卡片只是保留待处理记录；再次计时必须显式选择继续，从新锚点开始。放弃必须明确确认，不通过手势关闭隐式删除。
- 正式 Session 写入与未完成状态的消费必须具有原子/可恢复且幂等的语义。稳定操作 ID 防止双击、重复回调、重启补偿造成重复入账；旧回调不能覆盖后续编辑，不能复活已删除或已放弃记录。
- 保存失败保留待确认数据；在提交前后注入失败、进程重开后，结果只能是未完成状态仍可处理，或恰好一笔正式记录，不能两者都丢失或被统计两次。
- 所有成功声明以实际持久化为准；磁盘写失败时不承诺未落盘草稿跨强杀零丢失。正常进入后台保存恢复检查点；异常恢复不足以证明有效时长时进入待复核，不静默清空或自动入账。

### B. 手工记录、体验与纠错

- 活动、发生日期、投入时长为必要信息；日期默认为今天，也可历史补记。可选起止时间，不知道具体时刻也可保存。不是未来课程排程，计划时间不自动成为已参加事实。
- 体验采用轻量五档/类似单击选择，默认未填写，nil 不等于中档或零分；备注可为空、之后可编辑。文字可以描述活动内容、感受和下次继续点，不要求额外创建日记或多填必填框。
- V1 是本人自报体验，不将其默认为未来孩子自评或老师意见；来源语义应可扩展，但不开发家长/孩子/老师角色表单。
- 提供正常编辑、删除（确认）、取消和失败重试。手工新建/编辑与计时确认使用各自草稿，正常后台/中断可恢复已持久化草稿；显式取消不写正式事实，也不触碰旧记录。失败时不清空用户输入或原记录。
- 有精确区间的同一参与者记录重叠，给出可查看候选的提示，由用户修正或确认，不自动合并/删除/扣时。日期+时长没有精确重叠证据，只能标记疑似重复；重复提示与同一操作不得重复保存是两类不同约束。
- 活动改名不换 ID；已有关联记录/未完成计时的活动不提供级联硬删除，使用归档。归档保留历史和累计，已有未完成计时仍可处理；新开始/新补记先显式恢复该活动。V1 不要求活动合并或分类树。

### C. 历史与可信基础回顾

必选三个观察范围：每个活动自开始记录以来的全部累计、最近 7 天、最近 30 天。后两者为包含今天的自然日窗口，不是 N×24 小时滚动时长。活动筛选、历史明细、记录次数和按日趋势必须可下钻到同一批原 Session；旧记录不能因超过 30 天就不可查看。

统计只含正式保存记录。running、paused、待确认、异常恢复、未提交草稿不混入累计；可以单独展示进行中状态。归档活动默认仍属于历史总量，可筛选查看。无记录的日期是「无记录」，不是已知零投入或失败。

跨日口径固定如下，不留给实现者自行选择：
- 可信有效计时段按该 Session 保存的原时区的自然日边界分摊，暂停段不贡献任何一天；以后切换设备时区不重排已存事实。夏令时使用真实区间长度，不硬编码一天恒为 86400 秒。
- 纯日期+时长或修正后纯时长全部属于用户选择的发生日，不虚构可分摊区间。有效区间与纯时长都采用明确的精度标记。
- 跨日仍是一笔 Session；每日可显示该日有贡献的记录数，但周期记录次数按 Session ID 去重，不能把每日次数相加当周期次数。图表点击后只合计所选窗口内的贡献，同时可打开完整详情解释跨日部分。
- 示例：23:50–次日 00:20，中间 23:55–00:05 暂停，总投入 20 分钟，前日 5 分钟、次日 15 分钟，跨两日周期记录数为 1。

保存、编辑、删除、活动改名/归档后，当前已打开的汇总、图表、筛选和详情及时一致刷新；不靠退回重进碰巧刷新。统计与明细使用一致的事实快照/评价时刻。全部累计是已记录投入，不是客观技能水平或个人全天时间占比，不输出效率评分、孩子比较或 AI 结论。

## 四、页面集成与使用体验

保留 Today/Timeline/Record/Growth/Library 五 Tab，Record 仍直接打开图文记录；Today 体重/睡眠/目标/重要日子的原优先级和快捷操作保持。Growth 增加同级「时间投入」入口，包含活动卡、开始/记录活动、进行中/待处理状态、历史与回顾。

Today 仅在存在未完成计时/待确认事项时展示紧凑状态入口，无事项时不额外常驻大卡片；计时中可在 Growth 找回。不要为这个模块重写全局路由、Timeline 或全局搜索；本模块内活动查找/筛选为必选。

计时面板、手工记录与全局 Record 草稿相互独立；切 Tab、打开其他编辑器或旧通知路由不能覆盖草稿。首次提供一条可关闭的上下文说明，准确表达可切换其他 App、不以保持前台为前提；不宣称系统能自动证明实际参与。中文优先，保留英文、Light/Dark、较大动态字体、单手可触达按钮和 VoiceOver 基础标签。

## 六、迁移、备份与隐私不变量

### 6.1 原库安全与版本链

基线源码为 Schema V13 / 备份 v9。本期追加下一明确 Schema/备份版本（通常 V14/v10；执行时核实固定基线），保留历史版本标识、模型校验和和包契约。特别区分 V11Original=11.0 与 V11=11.1；不能通过修改它们共享的旧模型来偷偷改变历史 Schema。

复用现有迁移保护、StorePublication、隔离导入校验和发布路径；补齐新实体的快照、计数、引用验证、恢复、空库判断等所有实际入口，不只增加 Codable 字段。回归历史 V10、11.0、11.1、V12、V13 的真实合成磁盘库直接升级及重开；原已支持更早链路不削减。旧 Entry/图片、Habit、Weight、Todo、重要日子、Sleep、外部来源及相关收据保持。

迁移失败不清库、不覆盖已验证保护副本；验证 SQLite/WAL 等现行保护路径，不将很久前已有副本直接当作本次迁移前快照。旧保护副本不可擅自删除，必要修复限定在本轮升级安全范围内。

### 6.2 包恢复与运行状态是不同语义

新包完整保存参与者、活动、正式记录、时间证据、反馈以及可恢复的未完成检查点；旧包依版本读取，新包缺必需数组/非法字段不得通过 decodeIfPresent 默认空数组伪装成功。包计数、校验和、引用和版本字段必须一致；未知状态/来源、悬空 ID、重复 ID、一个参与者多未完成计时、非法时长与区间安全拒绝，不能静默丢弃。

导出中的未完成计时采用一致快照时刻 checkpointAt 固定已可信的累计证据，且不暂停/结束原 App 的计时。检查点时刻与所读状态必须一致，不能机械复用在异步快照开始前取得的 manifest 时间来计算新计时。

从包恢复不是恢复同一台设备正在运行的进程：所有未完成检查点进入「恢复后待确认」，不自动运行、不进入正式累计、不复用旧设备单调时钟锚点，也不补上导出至导入的间隔。恢复后可确认保存已有可信时长、修正、明确从现在继续或放弃；暂停/到目标/结束待保存的原语义保留为证据。示例：导出时 12 分钟，7 天后恢复，默认仍是待复核的 12 分钟，而非 7 天加 12 分钟。

保持现有只向空库恢复的边界，不扩展成合并或覆盖真实数据。新实体必须纳入预览与正式发布前的空库复核；预览后新建计时/记录必须使恢复安全失败，不能覆盖它。默认「我」和推荐活动的惰性初始化不能使新装 App 无法恢复；这条必须经过真实 App 入口验证，而非仅测试一个裸空 ModelContext。重复向非空目标导入必须拒绝且不改数据，不因按名字合并增加时长。

### 6.3 身份与隐私
