## 1. 产品定位与不变量

用户名称统一为「重要日子」。它不是待办，不是目标，不是日记类型，也不是完整日历。

### 必须保持的原则

- 先保存，再装饰和关联。创建一个可用日子不能强制选择照片、标签、提醒或关联对象。
- 日期经过不等于任务完成、习惯持续或成果实现。
- 关联引用现有内容，不复制正文、不伪造 Entry、不改变原始发生时间。
- 重要日子不使用红色逾期、完成勾选、失败惩罚或连续签到机制。
- 不默认庆祝。生日、旅行、离别、纪念等使用中性文字；装饰由用户决定。
- 不新增底部 Tab；不改变 Record 的默认流程；不借机重做整个 Today 或 Growth。
- 本地可用，不依赖 AI、网络、云账户或端侧大模型。
- 通知权限、外部组件可见性和 App 内展示分别管理，不互相暗含授权。

### 三种创建预设，而非三套实体

| 预设 | 用户意图 | 初始行为 |
| --- | --- | --- |
| 期待某一天 | 旅行、考试、演出、计划中的时刻 | 一次性未来日期，默认看剩余天数 |
| 记住一个起点 | 入职、搬家、开始学摄影等已发生节点 | 一次性起点，默认看已经过去的天数 |
| 每年纪念 | 生日、相识、周年 | 按公历或农历每年出现，默认看下一次 |

生日与周年可提供轻量示例，不建立必须维护的分类树。周年在已知起始年份时允许同时看“已经多久”和“距离下次周年”；切换展示不创建第二个日子。

一次性未来日到达后仍保留原对象。默认文案为“预定日已过 N 天”，而不是“旅行已进行 N 天”。用户可改期、归档或主动把实际发生日期确认为纪念起点，系统不代为确认事情已经发生。

## 2. 导航与页面位置

### 2.1 成长页：唯一稳定管理入口

保留既有四个入口，新增「重要日子」于体重之后、Quiet Wins 之前；保留它们之间的轻量视觉分组即可，不强制重排旧模块。

新入口可用 `calendar` 类图标，副标题为“记住值得期待和回看的日子”。有内容时可换成一条近期摘要，而不是必须显示“共 N 个”数字。首版不把倒数卡或 Quiet Wins 五张事实卡直接展开在 Growth 首页。

### 2.2 Today：条件出现、最多两行

建议插入位置：目标/标记之后、周/月习惯之前。今日习惯、体重和目标的相对位置不变。工具栏不再增加一个“日期”图标，也不把现有加号改成多功能菜单。

模块标题为「重要日子」，右侧“全部”。每行包括图标、名称、时间距离；需要时显示简短日期。没有候选时整段隐藏，不常驻空状态和新增按钮。

单个日子的 Today 设置为：

- 自动：当日或未来 7 个自然日出现的日期可以候选；普通过去起点不自动长期占位。
- 始终显示：允许用户主动长期关注一个起点或较远的未来日。
- 不显示：不进入 Today，仍可在管理页查看或独立设置提醒。

筛选首先排除归档和“不显示”。排序为：今天发生 → 用户选择始终显示 → 自动近期；各层以实际日期、稳定次序和 ID 处理平局。当天项目不能被一个多年以前的固定起点永久挤走。最多两条，余项进入“全部”。

“常看”仅决定管理页位置，不等于“始终显示在 Today”，也不等于“允许在桌面显示”。这些设置在详情中渐进呈现，不让创建表单初次出现一排开关。

### 2.3 Record、Timeline 与资料库

Record：原有一键图文记录不变。

Timeline：仍展示真实记录及既有事实，不因为新增日期、跨日或到达周年自动插入虚拟日记。日子的相关记录仍在原时间位置，只增加轻量关联标识和回跳入口。

资料库：不用再建立第二份日期管理列表。全局搜索加入“重要日子”结果类型，名称和简短说明可检索；结果按类型区分，而不是把日期与同名 Entry 合成同一条。归档结果遵守现有归档检索约定，并明确标识。

## 3. 创建与编辑

### 3.1 快速创建表单

单张表单完成，不做多页向导。

首屏可见：名称、预设、日期、按需出现的历法与年份信息、实时结果预览、保存。

低频选项放入“更多设置”：Today 展示、提醒、图标/颜色、封面、简短说明、特殊日期规则。保存不以这些字段为前提。

名称建议最长 80 个字符，但应在开发时与现有输入规范核对并明确最终上限。界面应支持长名称两行显示，不靠不可读的极小字号解决。

日期选定后给出明确预览，例如“距离下一次生日还有 N 天；对应公历日期为……”。农历切换必须展示日期转换结果；不能在用户不知情时把“同一个发生日换一种历法显示”和“按新历法重新指定日期”混为一谈。

### 3.2 不知道年份

每年纪念允许只知道月日，不填原始年份。此时只显示下一次日期和剩余天数，不计算年龄、几周年、累计已过天数。禁止填入虚构年份作为业务事实。

### 3.3 从 Entry 创建日子

在 Entry 详情的低频操作中提供“设为重要日子”。这是创建一个引用当前 Entry 的新日子，不是改变 Entry 类型。

标题可使用记录标题作为建议；日期使用可解释的 occurredAt 转换结果并让用户确认，不能采用 createdAt、updatedAt 或导入时间。旧记录没有原始当地时区证据时，不猜测当年的当地日期。

可使用记录中的图片作为封面来源，但要在保存时形成独立封面资源，不能暗中改变原记录图片的删除规则。

取消创建不留下半条日子、关联或封面；重复点击保存必须防重入。疑似同名同日只提示已存在，不强制合并两个真实不同的日子。

## 4. 管理页与详情页

### 4.1 管理页

默认紧凑列表，顶部搜索与新增。首版不同时开发卡片墙、月历、时间轴三套视图。

常看区使用明确手工顺序。其余项目分为有下一次日期的项目，以及没有下一次日期的过去起点；自动排序不改写用户常看顺序。同一个日子在当前列表中只出现一次。

每年纪念即使原始日期在过去，也归入“下一次”组。原始年份信息可作为副标题，而不是同时在过去和未来组重复一遍。

归档放到菜单或过滤项中，不默认挤占顶层。首次空状态用三种预设的例子说明“这里可以放什么”，示例不写入用户数据库。

### 4.2 详情层级

上部：名称、可选封面、时间距离、原始日期/下一次日期、必要的历法信息。

中部：主要动作“写一条相关记录”，次要动作“关联已有记录”。当用户从详情记录当下经历时，occurredAt 默认今天；不因为关联一个多年以前的日子而自动把新记录回填到起点那年。

下部：相关记录列表；存在关联 Todo 时显示一个紧凑的相关待办区；再往下是提醒状态和日子设置。不把详情扩展成第二个 Todo Hub 或复杂项目看板。

每年纪念允许在相关记录区查看不同年份/期次。基础关联固定在日子 ID 上，必要时记录明确的本次纪念日期。通用记录不强行绑定某一年；系统不凭记录创建时间自动声称这是哪一年的生日经历。

记录和日子之间双向跳转。返回时保留列表搜索、滚动位置和编辑状态。

## 5. 与现有功能的协同契约

### 5.1 Entry：第一优先级的深度连接

一个日子可关联多条 Entry；同一 Entry 可服务于多个日子。关系唯一性以两端稳定 ID 为基础，避免重复关联。

本轮增加或删除关联不改写原 Entry 的正文、图片、occurredAt、外部来源和技术更新时间。真正编辑 Entry 的内容才走原编辑服务。

删除日子只删除日子自有数据与关系，不删除 Entry。删除 Entry 清理或失效其引用，保留日子。详情显示当前仍然有效的内容，不显示僵尸链接。

### 5.2 Todo：V1 仅做用户主动创建的一次性行动

详情提供“添加相关待办”，复用现有 Todo 编辑器。例：在某次生日下添加“订蛋糕”。用户确认任务名称、计划日期和提醒后，才保存独立 Todo。

新关系需要明确的日子 ID 与可选期次日期，不能滥用现有 `TodoTaskSource.entryID`，也不能为了复用它伪造一条 Entry。

首版不支持相对日期自动同步、自动生成每年重复任务、级联取消或完成。日子改期后，关联 Todo 的日期不自动变化；提供“日子日期已变化，相关待办仍保留原安排”的检查入口。用户可用既有 Todo 编辑功能决定是否调整。

完成关联 Todo 只影响该任务及其既有统计；不会完成一个生日。删除日子不删除 Todo。关闭日子提醒不关闭 Todo 的提醒。

### 5.3 Goal 与 Habit：先保持语义边界

V1 不新增自动目标倒数，不补写 Goal 截止日期，不把 Habit.createdAt 当成真实开始日，不自动从最近一次打卡重置天数。

用户可手动建立“开始学摄影”的日子，并通过相关 Entry 回看实际过程。以后需要真正的目标/习惯关系时，再按真实使用反馈增加；不提前开发通用关系平台。

### 5.4 Quiet Wins：保持现有事实规则

新建、编辑、收藏、查看日子或更换封面，不进入成果统计。

从日子详情真实写出的普通生活记录，按现有 Entry 规则参与回顾；被关联的外部分享仍按来源证据处理，不能因为关联日子而重新归类为用户原创记录。同一 Entry 不按关联数量重复计数。

保留当前已接受的 v7 导入收据恢复限制，不把本轮备份版本扩展当成自动修复历史来源事实的授权。不能凭正文、标题或时间猜测缺失来源。

详情解析须继续以稳定 ID 和当前有效数据为依据，不依赖 Today 前两条、组件前三条或其他页面的排名快照。后台保存后的 UI 交付遵守主线程边界，避免复发最近已修复的问题。

## 6. 小组件：两个组件类型，三种视觉表达

### 6.1 指定日子：日历数字样式

参考截图的大数字日历卡，但采用随心 log 自己的系统字体、圆角、边距和主题色。

结构：小标题/图标 → “还有”或“已经” → 大数字与明确单位 → 简短日期。当天用“就是今天”，不用负数。数字采用易读等宽数字；不默认花体、金色相框、爱心或粉色主题。

支持小尺寸；中尺寸复用同一日子内容，只增加适度留白和必要副信息，不增加另一组功能。

### 6.2 指定日子：照片样式

与数字样式共用数据与设置，是外观切换，不是第二套日期功能。用户选择一张照片，调整裁切位置；文字区域有足够遮罩。重点仍是名称、时间关系和数字。

照片资源保存为重要日子的独立封面，复用现有文件处理/缩略图能力但不复用错误的所有权。封面是用户数据，应进入备份；Widget 用的小图是可重建缓存。更换、取消、低空间失败和删除不能留下失控的孤立资源。

关联 Entry 的原图删除后，明确保存为独立副本的封面可继续存在；界面在复制时说清“用作独立封面”。删除日子则清理它自有的封面和派生缓存。

### 6.3 日子清单：紧凑多日样式

中尺寸，最多三行。每行保留名称、还有/已过、数字与单位。避免将所有内容都铺成三个微型海报。

V1 由用户显式选择最多三个日子并确定顺序；未选择时不默认公开全部私人日子。删除或归档后保留明确空位/失效提示，不自动用另一个私人日子替换。自动从已授权候选中挑选近期项目放到后续版本，不作为首版要求。

小尺寸多日列表不作为首版硬要求，避免长名称和大字模式下不可读。

### 6.4 交互、隐私和降级

指定日子组件点击直达该日子详情。清单各行在系统允许的尺寸与链接方式下直达各自详情；否则给出可预测的清单落点，不声称每行都能独立点击。

路由使用稳定 ID，不使用列表位置。已删除、已归档或无权限内容显示明确状态，不自动跳到另一条私密日子。App 正在恢复、迁移或保留未保存的 Record 草稿时，先处理安全状态，再完成导航，不能清空草稿。

未配置、缓存损坏、资源缺失时使用中性占位，不拿真实私人记录充当 Gallery 示例。私密内容与系统隐私敏感机制配合，通知正文可选择通用描述。禁止暗中把全库文字或原图复制进共享目录。

适配浅色、深色、着色/透明等系统渲染模式；照片和遮罩不能只在全彩模式可读。大字号时可以减副信息或减少清单行数，不能单纯缩到不可读。

首版不承诺秒级倒计时，不做 Live Activities、Apple Watch 独立 App、锁屏组件全家桶或复杂主题市场。

### 6.5 引导

首次成功保存日子后给一条可关闭的组件提示；详情里保留“添加桌面小组件”的帮助入口。展示当前日子的真实预览与添加说明，不用首次打开即弹出的巨大营销遮罩。

说明页不得把“显示引导”冒称为“已经自动安装小组件”。

## 7. 日期与展示规则

### 7.1 存储语义

原始民用日期、历法、可选年份、重复规则与显示偏好分开。已经过 N 天、下一次日期、Today 排名和组件文案均为派生结果，不作为不断重写的事实字段。

历史发生日期不因切换手机时区而被改写。与“今天”的距离默认使用设备所在时区的自然日。农历换算使用明确一致的历法基准；对于中国农历，设计建议以中国民用历法/Asia/Shanghai 生成对应的公历民用日期，再进行展示，避免设备时区改变了同一农历日期的对应公历日。开发需要以独立核对样例验证，不能仅凭 API 名称认定正确。

来源记录转换的起始日必须可由用户确认。跨日、前台恢复、明显系统时间变化和时区变化时重新计算；不承诺系统未唤醒扩展时瞬间刷新所有组件。

### 7.2 天数与当天

“已经 N 天”表示经过 N 个自然日；起点当天为零，翌日为一。首版不增加含义容易混淆的“第 N 天/包含今天”切换。

未来日为“还有 N 天”；当日为“就是今天”；过去起点为“已经 N 天”；过去的预定日期为“预定日已过 N 天”。

年度纪念在当天全天仍显示今天这一期，次日才切换到下一期。周年数只有已知有效起始年份时才展示；不能把每年重复简单当成固定增加 365 天。

### 7.3 特殊日期

公历 2 月 29 日：首遇时让用户确认非闰年采用 2 月 28 日、3 月 1 日还是仅闰年。推荐选项可为 2 月 28 日，但不得静默隐藏该选择。

农历闰月：保存闰月语义并确认规则，例如“有相应闰月时用闰月，否则用同名普通月”。一年最多出现一次，不能普通月和闰月重复庆祝。

农历某月三十在当年不存在：明确选择该月最后一天或跳过，推荐最后一天并在预览中显示。不能凭 Foundation 默认匹配行为悄悄跨月。

特殊规则必须在详情可查，创建/编辑时可预览未来少量实际日期。首版仅支持经验证的日期范围，超范围明确提示，不能猜测或崩溃。

### 7.4 正数与周年共存

一个过去的相识日允许显示“已经 N 天”和“下一次周年还有 M 天”，但只需一条记录。用户为指定日子组件选择主要视角；App 详情保留另一个视角。

未知年份的生日只有下一次视角。不存在起始年就不存在可信年龄或累计天数。

## 8. 提醒与跨模块协同

提醒默认关闭；用户主动开启时才请求系统权限。支持当天、提前 1/3/7 天等少量预设，最多选两次，默认时刻建议上午 9 点并允许修改。

开启前展示实际下一次提醒日期、时刻和使用的时区。保存日子成功和通知成功必须分别报告：通知失败不能丢失已保存日子，也不能显示虚假的“已设置成功”。

建议沿用并协调现有通知服务：

- Todo、日子、每日记录和周回顾共享容量判断与串行提交边界。
- 使用各自稳定标识/前缀，禁止 removeAll 类清空操作误删其他功能通知。
- 不允许 Todo 算 60 条、重要日子再独立算 60 条。
- 容量不足明确显示未排期，按确定性优先级安排近期请求，不悄悄挤走其他类别后仍报告它已排好。
- 编辑、归档、删除、恢复和规则变更后取消失效请求并重新核对实际 pending。
- 已经发出的旧通知若指向被删除数据，点击能安全降级；需要清理时仅清理本模块对应通知。

年度提醒优先采用经过验证、能保持语义的系统重复触发；农历或特殊规则无法可靠直接重复时采用有界预排与补齐。详情需如实显示已排期覆盖范围和下一次真实请求，不宣称无限期离线提醒。长期不打开 App、时区变化及系统专注模式的实际表现进入真机验证。

本轮不重写 Todo 的重复期次、事件历史和完成统计。共享的只是权限/容量/调度协调，不是统一全部业务模型。

## 9. 最小实现结构与数据保护

### 9.1 合理的数据增量

建议有独立 ImportantDay 实体、Entry/Todo 的有类型关联、独立封面资源。具体 Swift 类型名可由开发者结合仓库约定选择，但不得用 Entry、Tag 或 Todo 的隐藏字段冒充新实体。

主日期对象至少表达：稳定 ID、标题、简短说明、创建预设/日期含义、历法与原始日期、年份是否已知、年度规则和例外策略、主要显示视角、Today 策略、常看顺序、归档状态、可选封面、提醒偏好、技术创建/更新时间。

关系只保存身份和必要的纪念期次信息，不复制对方正文或状态；派生结果不可替代真实关系。

### 9.2 唯一日期计算模块

App 内列表、详情、Today、通知计划和 Widget 使用同一套纯计算规则。输入为日期对象、参考自然日、历法/时区上下文；输出为时间关系、下一期与相关显示数据。

不能在五个页面各写一份日期相减。也不改写现有 Habit 的历史自然日证据规则。

### 9.3 组件只读共享展示数据

主 App 保存成功后，生成版本化的共享展示快照与按需封面缩略图，通过原子写入发布到 App Group。Widget 只读这些数据，结合日期规则生成时间线；不打开或迁移主 SwiftData 库，不消费 Share Inbox，不导入私人数据，不触发恢复服务。

快照包含适量的原始日期规则或已计算时间线材料，不仅是一张写死“还有 23 天”的截图。应能在不每日打开 App 的正常情况下按系统时间线改变天数。

快照带数据版本/生成标识；更新、删除、归档、恢复及筛选变化触发重建与 reload 请求。发生生成失败时，主 App 仍正常保存和使用；错误状态可诊断，不能阻塞入口。恢复、删除和隐私变更尤其不能靠无限期使用旧缓存掩盖失败。

系统控制 Widget 刷新时机，不能承诺每次修改、午夜和时区跳变都毫秒同步。测试目标是提交一致数据、正确时间线和可靠恢复，而不是伪造系统保证。

### 9.4 版本化升级与备份

新增 Schema 版本和备份版本必须明确；既有历史 Schema 定义与 preMigrationProtection 修复不随意改写。保留 Bundle ID、原主库位置和原用户数据，不为组件迁移主数据库进 App Group。

新备份覆盖日期事实、农历/闰月/特殊规则、关系、封面和提醒偏好。组件缓存不必成为事实备份，恢复后重建。

新版本能够读取当前支持的旧包；旧版本无法理解新包时应明确拒绝，不允许导出文件表面成功却静默漏掉全部日子。原本已接受的 v7 收据丢失边界如实保留，不伪造来源。

备份恢复后的提醒属于当前设备排期，要重新检查权限和实际请求，不能把备份里的“已排好”状态直接当作恢复成功。Widget 配置引用稳定 ID；旧引用不存在时安全占位。

## 10. V1 范围与后置项

### V1 完整目标

- 三种创建预设，公历/农历，自然日正倒数，每年纪念，未知年份与特殊日期规则。
- 管理列表、常看、搜索、归档、编辑、删除及可恢复的失败表现。
- Today 条件摘要，不改变现有五个 Tab 与快速记录。
- Entry 双向关联、相关记录创建；一次性 Todo 手动创建与关联，不自动联动状态/日期。
- 两种 Widget 类型：指定日子与日子清单；指定日子包含数字/照片外观。
- 适度本地提醒、共用调度容量与真实状态反馈。
- 独立封面、数据升级、完整导入导出、路由与隐私降级。
- 中文/英文、浅深色、大字号与基础无障碍。

### 后置，不作为本次完成条件

百日/千日等任意里程碑提醒；目标截止日期/习惯自动计时；相对日期自动改 Todo；跨人共享/情侣空间；云同步重构；AI 总结；联系人/系统日历自动导入；复杂分类；完整日历；主题商店；视频模板；Live Activities；独立 Watch/Mac 功能；锁屏组件扩展矩阵。

复杂纪念日里程碑可以先在以后版本作为只读展示讨论，不能借此把 V1 扩大到全面时间管理。

## 11. 交付顺序与验证成本

整个 V1 建议分两个有边界的实现批次，不拆成长期漂移的多个产品版本：

A. 日期规则、数据升级/备份、管理和详情、Entry/Todo 最小关系、Today、提醒协调。

B. 数字/照片/清单组件、原子展示缓存、路由、隐私、系统渲染模式和端到端收口。

组件在 B 完成，不无限期列为未来愿景。正式开始前只做必要的基线/分支核对；中间针对变动运行定向测试；交付前做一次集中回归与独立 review。不要每个 UI 小调整都重复全量测试，也不要把任务写成无限自主循环。

Widget 签名与 Xcode Cloud 包含关系在 B 尽早核对，不能到发布最后一步才发现 Extension 未打包。本设计与配套 Goal 均不授权自动合并、tag、Archive、发布 TestFlight 或操作真实手机数据。

## 12. 验收矩阵

| 场景 | 必须通过的结果 |
| --- | --- |
| 创建一个未来旅行日 | 名称与日期即可保存；数字清晰；无强制照片/提醒 |
| 未来日跨到当天及次日 | 当天保持“就是今天”；次日不声称旅行实际发生 |
| 回填一个过去起点 | 起点保持；首次创建时间不替代发生日 |
| 公历生日、未知年份 | 下次日期正确；无虚构年龄/周年/累计天数 |
| 农历生日、跨年 | 每年按正确规则出现；不锁死首次换算的公历日期 |
| 闰月、农历三十、2月29日 | 特殊规则可见且结果有独立核对样例；不静默跨月 |
| 时区、夏令时、跨日 | 主规则一致；不把自然日误算成24小时块；原始日期不变 |
| 给五年前的日子写今天的记录 | 新记录默认今天；原 Entry 不改时间、不复制 |
| 给同一 Entry 关联两个日子 | 能分别回看；Quiet Wins 不重复计数 |
| 关联 source=nil 外部分享 | 本地现有收据证据继续起作用；不因关系变成原创 |
| 创建相关 Todo 后改期日子 | Todo 不被静默改期；用户能看到并检查差异 |
| 多种提醒同时存在 | 不相互清空；容量满、拒权和失败真实可见 |
| 重命名/改期/归档/删除 | App、缓存、通知计划按同一新版本更新 |
| 更换封面后取消/失败 | 旧封面仍有效或有明确恢复；无孤立伪 Entry |
| 删除来源 Entry | 日子仍在；相关引用安全失效；独立封面按明确所有权保留 |
| 新版备份→空库恢复→重开 | 日子、规则、关系、封面保留；提醒和组件状态重建 |
| 从现有版本覆盖升级 | 原记录、图片、习惯、目标、体重、Todo、来源数据不丢失 |
| 从组件冷启动/已有草稿时打开 | 路由正确，不清空 Record 草稿，不绕过存储恢复界面 |
| 组件长期不打开 App | 正常时间线继续提供日期变化；不依赖每天前台写一次数字 |
| 组件着色/深色/大字号 | 照片不吞字，时间方向可读；无私密示例泄露 |

单元测试应允许注入固定时钟、时区、通知客户端和数据版本，避免依靠真实等待到午夜。农历关键期望值需独立核对，不让被测计算函数生成自己的标准答案。

Owner 真机验证可收敛为四个日子：未来旅行、过去起点、农历生日、已有图文记忆的周年。代码侧负责覆盖大量边界，不能把几十个人工复现场景都转嫁给用户。

## 13. 如何判断新增功能真的有价值

不以增加多少主题、用户每天进入几次页面或生成多少系统通知衡量。

建议看：用户是否在不重复录入的情况下保存了真正关心的日期；桌面或 Today 是否能一眼回答时间距离；是否自然写出或找回至少一条相关记录；新增功能是否没有让原本的记录、打卡、记体重与待办变得更慢。

> V1 的终点是“日期、提醒、桌面可见性和真实记录连接形成完整体验”，不是“复制一个越来越大的 Days Matter”。
