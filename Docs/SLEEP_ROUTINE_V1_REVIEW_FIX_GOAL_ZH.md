## 2. R1 — 回顾数据与评价时钟不同步

先检查真实呈现和通知接线。外部探针只证明判定链，不证明任何特定 iOS sheet 生命周期；补真实页面级测试，不通过强行改测试生命周期伪造反例。

## 3. R2 — 初始关闭保存不应消耗首次启用语义

### 最短反例

没有目标历史时，默认关闭开关点保存调用 setGoal(nil)，服务插入今天的禁用规则；当天第一次开启目标时，proposedDay 因 rules 非空推迟至明天。

### 最小修复

没有目标历史且目标仍关闭时，服务层保存是 no-op，不新增规则或伪造一次生效。界面可同步禁用无实际变化的保存，但不能仅依靠 UI 挡住。保留明确首次启用今日生效、后续修改/关闭下一起床日生效和历史不可回写。

不删除/重写已有真实禁用历史，不按猜测批量清洗旧规则；旧候选已存在的 nil 规则如需特殊处理，先证明必要性，不把它扩大成迁移任务。

### 验证

在真实 SleepService/ModelContext 中：初始关闭保存一次/多次后规则数仍为零；随后首次启用当天生效且重开保持。已经启用过的目标再修改/关闭、未来待生效规则编辑、回拨和跨时区保护仍正确。补设置界面路径或与 R1 集中 UI 合并验证，不新增完整的目标系统。

## 4. R3 — 提醒批次末尾 pending 缺失不等于提交失败

### 必须核实的时序

首次启用时 08:59:59 add 当天09:00成功，其余提交/确认期间到09:00并正常递送；最后 pending 已无当天ID。当前尾部只把仍pending的请求写入台账，随后把不在pending的成功请求改failed；当天防重复证据丢失，改到11:00可能再次排当天。

### 最小修复

区分成功提交、明确提前取消、已经到期/实际递送证据以及真实失败。成功提交的防重复证据不能只依赖批量末尾 pending 命中；过期状态和 UI 必须诚实，不能把未在pending直接等同 add 失败。

允许围绕现有客户端、协调器及 SleepReminderHistory 作小范围扩展，不要求新通知框架。不新增权限、不引入服务端。若需要扩展本设备 UserDefaults 排期元数据，保留旧值可读和原键兼容、明确重启行为；这不是新增 SwiftData Schema 或备份版本的授权。

- 只有“成功接受且到期”的证据时，不宣称系统已经显示/用户已经收到；实际 delivered 与保守 elapsed 语义分开。
- add 失败、未来请求意外缺失不能被统一改成成功；用户拒权/容量不足仍诚实。
- 真正提前取消的请求仍能按原规则重新排期；不能为了防重复而永远锁住日期。
- 接受后未确认前的 generation 变化不能抹掉真实操作证据或发布过期设置。只取消本类/本次应取消请求，不 removeAll，不影响其他类别状态。

### 验证

使用实际 TodoReminderCoordinator + 可控通知客户端，在一次 reconcile 内让当前请求 add 成功，再在最后 pending 前推进合成时间并令其递送/移出pending；主断言为不误报提交失败、当天防重复证据保留、随后改晚不再排当天，重建History/Coordinator后同样成立。

保留提交确认后才递送的正对照、真实提前取消后允许重排、失败和未来请求缺失、generation交错、关闭/恢复/删除记录、Todo/重要日子/每日/周回顾容量与状态。不要只测独立改写出来的调度尾段，不等待真实09:00，不以模拟客户端结果冒充真机递送。
